Agent Teams 첫인상: 이렇게 돌아갑니다

지금까지 복잡한 작업은 서브 에이전트에게 맡겨 왔습니다. 코드 리뷰어, Next.js 개발자, UI 마크업 전문가… 각 분야의 전문가에게 일을 위임하고 결과를 받는 방식이었죠.

그런데 여기에 한 가지 한계가 있습니다. 서브 에이전트들은 서로 대화하지 않습니다. 각자 독립적으로 일하고, 결과만 돌려줍니다.

이번 챕터에서 만나는 Agent Teams는 바로 그 한계를 넘어섭니다. 개념 설명보다 실제로 돌아가는 화면을 먼저 보여 주는 챕터라, 부담 없이 구경하는 마음으로 따라가면 됩니다.

"자, 그러면 본격적으로 에이전트 팀을 배우기 전에 실제 화면을 보면서 그 특징을 간략히 설명드리도록 할게요. 진짜 부담 없이 들으셔도 돼요."

팀장의 두 가지 상황

강사는 회사 팀장의 입장으로 개념을 설명합니다. 팀장에게는 두 가지 상황이 있습니다.

상황 1 — 각자 알아서 하면 되는 일. 서로 얽힐 게 없는 독립적인 업무 네 개가 있습니다.

"이럴 때는 팀원 4명에게 하나씩 맡기면 돼요."

각자 자기 일을 하고 결과만 가져오면 그만입니다. 이것이 지금까지 써 온 서브 에이전트 방식입니다.

상황 2 — 서로 맞춰 가며 해야 하는 일.

"근데 이건 아까와는 상황이 다릅니다."

시장 조사 결과를 봐야 예산을 짤 수 있고, 경쟁사 분석 내용이 일정에 영향을 줍니다. 이럴 땐 팀원들이 서로 소통하며 진행해야 합니다. 이것이 Agent Teams입니다.

방식 일하는 모습
서브 에이전트 각자 독립적으로 일하고 결과만 전달
Agent Teams 하나의 팀을 이뤄 서로 소통하며 협업

시연: 도시락 배달 서비스 기획안 만들기

말로만 하면 감이 안 오니 실제 예시를 봅니다. 주제는 직장인 점심 도시락 배달 서비스 런칭 기획안 작성입니다.

흐름은 이렇습니다.

  1. 팀원 4명을 생성합니다.
  2. 각자에게 태스크를 분배합니다.
  3. 팀원들이 동시에 작업을 진행합니다.
  4. 팀장에게 진행 상황을 물어봅니다.
  5. 완료된 보고서들을 종합해 최종 기획안을 만듭니다.

분배된 태스크는 다음 네 가지입니다.

담당 태스크
팀원 1 시장 조사
팀원 2 경쟁사 분석
팀원 3 예산안 작성
팀원 4 일정표 작성

명령을 내리면 팀이 생성되는 모습이 그대로 보이고, 각 팀원이 자기 작업을 진행합니다. 중간에 팀장에게 "지금 어떻게 되고 있어?"라고 물으면 진행 상황을 피드백해 줍니다.

"그러면 팀장이 우리에게 진행 상황을 피드백한 걸 확인할 수 있고요."

그리고 작업이 끝나면 흩어져 있던 네 개의 보고서가 하나의 기획안으로 종합됩니다.

"깔끔하죠?"

화면 구조: 팀 리드와 팀 메이트

이제 화면이 어떻게 구성되어 있는지 살펴봅니다. 크게 좌우로 나뉩니다.

위치 역할 정체
좌측 팀 리드 (Team Lead) 내가 실행한 Claude Code 세션
우측 (분할) 팀 메이트 (Team Mate) 각각 독립된 Claude Code 세션

여기서 놀라운 점이 있습니다. 팀 메이트는 단순한 하위 프로세스가 아니라 각각이 독립된 Claude Code 세션이라는 것입니다. 우측 화면이 여러 개로 분할되어, 여러 세션이 동시에 돌아가는 모습을 실시간으로 볼 수 있습니다.

"우측에 보이는 이러한 분할된 화면은 팀 메이트, 즉 팀원인데요."

팀 리드는 우리가 명령을 내리는 창구입니다. 작업을 분배하고, 진행 상황을 취합하고, 결과를 종합합니다. 회사의 팀장이 하는 일과 정확히 같습니다. 그리고 팀 메이트는 필요에 따라 팀 리드가 추가 합니다.

진짜 차이: 팀원들이 서로 소통한다

Agent Teams의 정체성이 여기 있습니다. 팀원들은 격리된 채로 일하지 않습니다.

협업 수단 내용
메시지 팀원끼리 메시지를 주고받음
Task List 공유 누가 무엇을 하고 있는지 함께 봄

그래서 시장 조사를 맡은 팀원의 결과가 예산을 짜는 팀원에게 전달되고, 서로의 진행 상황을 보며 작업을 맞춰 갈 수 있습니다. 결과만 모으는 것과 과정에서 맞춰 가는 것의 차이입니다.

팀원에게 직접 말 걸기

한 가지 더 인상적인 장면이 있습니다. 우리가 소통할 수 있는 대상이 팀 리드만은 아니라는 것입니다.

강의에서는 경쟁사 분석을 맡은 팀원에게 직접 메시지를 보내 인사를 나누고, 협업 전략을 논의하는 모습을 보여 줍니다. 팀장을 거치지 않고 담당자와 바로 이야기하는 셈이죠.

의미. 팀 리드에게 지시하는 하향식 흐름만 있는 게 아니라, 특정 담당자와 직접 실시간으로 소통할 수 있습니다. 결과가 마음에 들지 않을 때 그 담당자에게 직접 방향을 잡아 줄 수 있다는 뜻입니다.

서브 에이전트와 무엇이 다른가

첫인상 챕터인 만큼 세부 사용법보다는 차이의 감각을 잡는 것이 목적입니다. 정리하면 이렇습니다.

비교 항목 서브 에이전트 Agent Teams
실행 단위 위임된 작업 독립된 Claude Code 세션
상호 소통 없음 (각자 독립) 메시지·Task List 공유
결과 취합 각각의 결과를 받음 팀 리드가 종합
사용자 소통 메인 세션과만 팀 리드 + 팀원에게 직접
적합한 작업 서로 얽히지 않는 작업 맞춰 가며 해야 하는 작업

서브 에이전트가 "외주 4곳에 나눠 맡기기" 라면, Agent Teams는 "한 팀을 꾸려서 같이 일하기" 입니다.

정리하며

이번 챕터는 Agent Teams의 첫인상을 잡는 시간이었습니다.

  1. 서브 에이전트는 각자 독립적으로 일하지만, Agent Teams는 서로 소통하며 협업합니다.
  2. 화면 좌측은 팀 리드 (내 세션), 우측 분할 화면은 팀 메이트 (독립 세션들)입니다.
  3. 팀원들은 메시지와 Task List를 공유하며 함께 작업합니다.
  4. 팀 리드는 작업을 분배하고 진행을 취합하고 결과를 종합합니다.
  5. 우리는 팀 리드뿐 아니라 팀원에게 직접 말을 걸 수도 있습니다.

핵심은 "위임"에서 "협업"으로 넘어갔다는 점입니다. 지금까지는 AI에게 일을 나눠 주는 쪽이었다면, 이제는 AI들끼리 팀을 꾸려 일하고 우리는 그 팀을 운영하는 그림이 됩니다. 다음 챕터에서는 서브 에이전트와의 차이를 더 깊이 파고들어 봅니다.

서브에이전트 vs Agent Teams: 차이점과 5가지 핵심

앞 챕터에서 Agent Teams가 돌아가는 모습을 구경했습니다. 이제 제대로 이해할 차례입니다. 그런데 Agent Teams를 이해하는 가장 좋은 방법은 기존 서브 에이전트와 무엇이 다른지를 아는 것입니다.

"그래서 본격적으로 들어가기 전에, 이전 강의에서 다룬 서브 에이전트에 대해 간단히 복습하도록 할게요."

복습: 서브 에이전트는 왜 좋았나

서브 에이전트의 장점은 명확했습니다. 메인 컨텍스트와 분리된 별도의 컨텍스트에서 작업하고, 결과만 요약해서 돌려준다는 것이죠.

덕분에 메인 컨텍스트를 아끼면서 복잡한 작업을 이어 갈 수 있었습니다. 앞선 프로젝트들에서 코드 리뷰나 DB 설계를 서브 에이전트에게 맡겼던 이유가 바로 이것입니다.

그런데 이런 한계가 있습니다

문제는 작업이 복잡해질 때 드러납니다. 서브 에이전트에는 세 가지 한계가 있습니다.

한계 무슨 뜻인가
에이전트 간 대화 불가 서브 에이전트끼리는 서로 이야기할 수 없음
중간 분석 결과 소실 결과만 요약해 반환하므로 과정에서 얻은 정보가 사라짐
메인 에이전트의 관리 부담 모든 조율을 메인이 혼자 떠안음

세 번째가 특히 뼈아픕니다. 서브 에이전트가 여러 개면 메인이 전부 중계해야 하는데, 그 조율 대화가 전부 메인 컨텍스트에 쌓입니다.

"결국 메인 컨텍스트가 이러한 조율 작업으로 빠르게 컨텍스트가 차버린다면, 더 복잡한 작업을 이어 나가는 것도 무리가 있을 거예요."

컨텍스트를 아끼려고 도입한 서브 에이전트인데, 조율 비용 때문에 오히려 컨텍스트가 차는 역설이 생기는 것입니다.

Agent Teams의 발상

그래서 나온 발상이 간단합니다. 팀장이 모든 것을 중계하지 말고, 팀원끼리 직접 이야기하게 하자. 그리고 작업도 스스로 나눠 갖게 하자.

한 줄 요약이 아주 명쾌합니다.

"Subagent는 시키면 혼자 다 하고 결과만 보고하는 프리랜서라면, Agent Teams는 서로 대화하면서 같이 일하는 하나의 팀입니다."

네 가지 축으로 비교하기

두 방식을 네 가지 관점에서 비교하면 차이가 선명해집니다.

관점 서브 에이전트 Agent Teams
컨텍스트 결과만 반환 → 중간 결과 소실 각자 독립 컨텍스트 유지 → 중간 결과 보존
소통 에이전트 간 대화 불가 팀원끼리 직접 메시지 교환
조율 메인이 전부 관리 공유 태스크 리스트로 팀원이 스스로
비용 상대적으로 저렴 독립 세션이므로 비용 높음

마지막 줄은 솔직하게 짚고 갈 필요가 있습니다. 팀원 하나하나가 독립된 Claude 세션이기 때문에, Agent Teams는 서브 에이전트보다 비용이 더 나갑니다. 좋은 기능이라고 아무 데나 쓸 일은 아니라는 뜻입니다.

5가지 핵심 용어

Agent Teams를 다루려면 알아야 할 용어가 다섯 개 있습니다. 강사는 회사 조직에 비유해 설명합니다.

"회사로 비유하면 이래요."

① 팀 리드 (Team Lead)

팀을 만든 Claude Code 세션입니다. 우리 (사장)는 팀 리드에게 지시를 내리고, 팀 리드가 팀을 굴립니다.

주의. 팀 리드는 한 번 정해지면 변경할 수 없습니다. 팀을 생성한 세션이 계속 팀장 역할을 맡습니다.

② 팀 메이트 (Team Mate)

팀 리드가 만든 추가 Claude Code 세션입니다. 각 팀원은 독립된 컨텍스트에서 작업합니다. 이 독립성이 앞서 말한 "중간 결과 보존"의 근거입니다.

③ 스폰 (Spawn)

새로운 팀원 세션을 생성하는 행위를 말합니다. "팀원을 스폰한다"는 곧 "새 세션을 띄운다"는 뜻입니다.

④ 태스크 리스트 (Task List)

모든 팀원이 공유하는 작업 목록입니다. 리드가 생성하고, 각 작업은 상태를 가집니다.

상태 의미
대기 중 아직 아무도 안 잡은 작업
진행 중 누군가 작업 중
완료됨 끝난 작업

할당 방식은 두 가지입니다.

  • 리드가 직접 지정 — "이건 네가 해"
  • 팀원이 스스로 가져감 — 대기 중인 작업을 알아서 집어 듦

두 번째 방식이 핵심입니다. 팀원이 알아서 일을 가져가면 리드의 조율 부담이 줄어듭니다. 앞서 지적한 "메인 에이전트의 관리 부담" 문제를 정확히 겨냥한 설계입니다.

⑤ 메일박스 (Mailbox)

팀원 간 메시지를 주고받는 시스템입니다. 리드↔팀원은 물론 팀원↔팀원도 소통할 수 있습니다. 앞 챕터에서 우리가 특정 팀원에게 직접 말을 걸 수 있었던 것도 이 메일박스 덕분입니다.

활성화 방법

Agent Teams는 아직 실험적 (experimental) 기능입니다. 그래서 기본으로 켜져 있지 않고, settings.json에 환경 변수를 설정해 활성화해야 합니다.

활성화한 뒤에는 특별한 명령어가 필요 없습니다. 자연어로 팀 구성을 요청하면 됩니다. 그러면 팀이 생성되고 태스크 리스트가 작성되며, 각 팀원의 개별 세션과 작업 상태, 그리고 팀 리드의 종합 보고까지 확인할 수 있습니다.

디스플레이 모드 두 가지

팀원들을 화면에 어떻게 띄울지도 선택할 수 있습니다.

모드 방식 준비물
In-Process Shift + 방향키로 팀원 세션을 순환 없음 (기본 모드)
Split-Panes 화면을 분할해 동시에 표시 tmux 또는 iTerm2

앞 챕터에서 본 인상적인 분할 화면이 바로 Split-Panes 모드입니다. 여러 세션이 동시에 돌아가는 걸 한눈에 볼 수 있어 보기엔 좋지만, 별도 터미널 도구가 필요합니다.

Windows 사용자라면 기본값인 In-Process 모드를 권장합니다. 추가 설치 없이 Shift + 방향키로 팀원들을 번갈아 보면 됩니다.

그래서 언제 전환해야 하나

이 챕터에서 가장 중요한 판단 기준입니다. 결론은 명확합니다.

상황 선택
작업들이 서로 독립적이다 서브 에이전트
팀원 간 소통·정보 공유가 필요해진다 Agent Teams
메인이 조율에 부담을 느낀다 Agent Teams

Agent Teams가 더 새롭고 강력해 보이지만, 비용이 더 든다는 점을 기억해야 합니다. 독립적인 작업 네 개를 굳이 팀으로 묶을 이유는 없습니다.

그리고 강사는 감이 안 오는 것도 자연스럽다고 말합니다.

"아마 지금 할 작업에 대한 업무 경험이 있으신 분들은 '어? 이러한 작업은 혼자 해도 되겠다'라는 느낌이 있으실 테고, 이 업무에 대한 경험이 적으신 분들은 '언제 Agent Team을 사용해야 하지?' 느낌이 안 올 수 있어요."

판단이 어렵다면 AI에게 물어보는 것도 방법이고, 결국은 반복해서 써 보며 감을 익히는 수밖에 없습니다. 사람 팀을 운영할 때도 "이건 혼자 시켜도 되겠다 / 이건 같이 붙어야겠다"는 판단은 경험에서 나오니까요.

정리하며

이번 챕터에서는 두 방식의 차이를 구조적으로 정리했습니다.

  1. 서브 에이전트의 한계는 대화 불가·중간 결과 소실·메인의 조율 부담 세 가지입니다.
  2. Agent Teams는 팀원 간 직접 소통과 자율적 작업 분배로 이를 해결합니다.
  3. 핵심 용어는 팀 리드·팀 메이트·스폰·태스크 리스트·메일박스 다섯 가지입니다.
  4. 아직 실험적 기능이라 settings.json 설정이 필요하고, 표시 모드는 In-Process / Split-Panes 두 가지입니다.
  5. 독립적인 작업은 서브 에이전트, 소통이 필요해지는 순간 Agent Teams로 전환합니다.

가장 기억할 문장은 역시 이것입니다 — 서브 에이전트는 프리랜서, Agent Teams는 하나의 팀. 프리랜서에게 맡길 일과 팀을 꾸려야 할 일을 구분하는 것, 그것이 이 기능을 잘 쓰는 출발점입니다. 다음 챕터에서는 Agent Teams를 비용 효율적으로 쓰는 방법을 살펴봅니다.

Agent Teams 심화: 비용 절반으로 줄이는 4가지 방법

앞 챕터에서 Agent Teams가 서브 에이전트보다 비용이 많이 든다는 점을 짚었습니다. 팀원 하나하나가 독립된 Claude Code 세션이니 당연한 일이죠.

그럼 비싸서 못 쓰는 기능일까요? 그렇지 않습니다. 이번 챕터에서는 비용은 줄이면서 품질은 높이는 방법을 다룹니다.

"이러한 방법은 딱 4가지만 적용하면 되는데요."

먼저 알아야 할 것: 팀원은 '풀 세션'이다

절약 방법에 들어가기 전에, 왜 Agent Teams가 비싼지 정확히 알아야 합니다. 앞 챕터에서 다룬 차이를 로딩되는 것 관점에서 다시 보면 이렇습니다.

구분 실행 환경 로드되는 것
서브 에이전트 격리된 컨텍스트 스킬은 명시적으로 지정해야 로드
Agent Teams 독립된 Claude Code 세션 메모리 파일·MCP·스킬을 전부 자동 로드

이것이 비용의 근본 원인입니다. 팀원 한 명이 스폰될 때마다 CLAUDE.md도, 연결된 MCP도, 설치된 스킬도 전부 그 세션에 올라갑니다. 팀원이 넷이면 그게 네 번 반복되는 것이죠.

뒤집어 보면. 팀원은 완전한 Claude Code 세션이라 별도 세팅 없이도 프로젝트 규칙과 도구를 다 갖추고 시작합니다. 비용이 드는 만큼 준비된 상태로 일한다는 뜻이기도 합니다.

그리고 여기서 앞선 「주제별 심화」에서 배운 것들이 그대로 유효해집니다. CLAUDE.md를 500줄 이하로 유지하고, MCP는 Tool Search로 관리하는 것 — 그 다이어트 효과가 팀원 수만큼 곱해져서 돌아옵니다.

방법 ① 계획 승인 모드로 헛수고 막기

첫 번째 방법입니다. 팀을 만들 때 계획 승인 모드를 적용하면, 팀원은 코딩을 시작하기 전에 계획을 제출하고 승인을 받아야 합니다.

왜 이게 절약일까요?

가장 비싼 토큰은 잘못된 방향으로 쓴 토큰입니다. 팀원이 엉뚱한 방향으로 30분간 코드를 짜고 나면, 그 토큰은 물론이고 되돌리는 데 드는 토큰까지 날아갑니다.

계획 단계에서 걸러 내면 실행 전에 방향을 바로잡을 수 있습니다. 시리즈 내내 반복된 "바로 고치지 말고 Plan 모드로" 원칙이, 팀 단위에서는 훨씬 큰 효과를 냅니다. 혼자 작업할 때보다 잘못된 방향의 대가가 팀원 수만큼 커지기 때문입니다.

한 걸음 더 나아가면, 리드가 판단 기준을 프롬프트에 미리 넣어 두고 자동으로 계획을 검증하게 할 수도 있습니다. 사람이 매번 계획을 읽고 승인하지 않아도 되는 것이죠.

방법 ② 모델 믹싱 — 리드는 Opus, 팀원은 Sonnet

가장 효과가 큰 방법입니다.

"이게 핵심인데요."

먼저 구조를 이해해야 합니다. Agent Teams의 토큰 사용량은 활성 팀원 수에 비례합니다. 그런데 모든 팀원을 Opus로 설정하면 어떻게 될까요?

앞 챕터에서 확인했듯 Opus는 Sonnet보다 토큰을 4~5배 씁니다. 여기에 팀원 수까지 곱해지면 비용이 폭발합니다.

그래서 나온 전략이 모델 믹싱 (Model Mixing) 입니다.

역할 모델 이유
팀 리드 Opus 계획·분배·종합 등 판단이 중요한 역할
팀 메이트 Sonnet 정해진 작업을 실행하는 역할

머리를 써야 하는 리드에게만 비싼 모델을 주고, 실행을 맡는 팀원들은 Sonnet으로 돌리는 것입니다.

"이것만 제대로 해도 비용이 확 줄어들어요."

앞선 챕터에서 배운 opusplan (계획은 Opus, 실행은 Sonnet)과 같은 발상입니다. 이번엔 그 구분이 시간 축이 아니라 역할 축으로 적용된 것이죠.

방법 ③ 훅으로 자동 품질 게이트 만들기

세 번째는 비용보다 품질 쪽에 가깝지만, 결국 비용으로 이어집니다. 품질이 나쁘면 다시 만들어야 하고, 그게 곧 토큰이니까요.

Claude Code의 훅 (Hooks) 을 활용하면 팀원의 작업에 자동 검증을 붙일 수 있습니다. Agent Teams용 훅이 두 가지 있습니다.

훅 언제 발동되나 검증 단위
TaskCompleted 팀원이 특정 Task를 완료했다고 선언할 때 개별 태스크
TeammateIdle 팀원이 할 일을 다 마치고 유휴 상태가 될 때 팀원 전체 작업

TaskCompleted 는 작업 하나가 끝날 때마다 검사하는 촘촘한 게이트이고, TeammateIdle 은 그 팀원이 손을 놓는 시점에 전체를 점검하는 게이트입니다.

여기에 린트나 타입 체크, 테스트 실행 같은 검증을 걸어 두면 — 사람이 지켜보지 않아도 팀원들이 만든 결과물의 품질선이 유지됩니다. 앞선 프로젝트 챕터들에서 매번 손으로 돌리던 타입 체크·빌드 테스트를 자동화하는 셈입니다.

방법 ④ 브로드캐스트를 아껴 쓰기

마지막은 놓치기 쉬운 포인트입니다. 브로드캐스트 (Broadcast) 는 모든 팀원에게 동시에 보내는 전체 공지입니다.

편리해 보이지만 함정이 있습니다.

주의. 브로드캐스트는 팀원 수만큼 토큰을 소모합니다. 팀원이 다섯이면 같은 메시지가 다섯 번 들어가는 셈입니다.

그래서 중요한 것이 규칙을 어디에 배치하느냐입니다.

성격 배치 위치
팀 전체가 항상 지켜야 할 규칙 CLAUDE.md 등에 미리 정의
그때그때 필요한 공지 브로드캐스트

매번 브로드캐스트로 "이 컨벤션 지켜 주세요"라고 외치는 대신, 처음부터 메모리 파일에 넣어 두는 것이 훨씬 저렴합니다. 팀원 세션은 어차피 메모리 파일을 자동으로 로드하니까요.

"생각보다 심플한데요."

네 가지를 한눈에

# 방법 효과
① 계획 승인 모드 잘못된 방향으로 쓰는 토큰을 사전 차단
② 모델 믹싱 리드만 Opus → 비용 대폭 절감
③ 훅 품질 게이트 자동 검증으로 재작업 비용 감소
④ 브로드캐스트 절제 규칙은 메모리에, 공지만 방송 → 중복 제거

②가 즉효약이라면, ①과 ③은 낭비를 구조적으로 줄이는 방법이고, ④는 습관의 문제입니다.

정리하며

이번 챕터에서는 Agent Teams를 감당 가능한 비용으로 쓰는 법을 배웠습니다.

  1. 팀원은 독립된 Claude Code 세션이라 메모리·MCP·스킬을 전부 로드합니다 (= 비용의 원인).
  2. 계획 승인 모드로 구현 전에 방향을 검증합니다.
  3. 모델 믹싱 — 리드는 Opus, 팀원은 Sonnet.
  4. TaskCompleted·TeammateIdle 훅으로 자동 품질 게이트를 만듭니다.
  5. 브로드캐스트는 아껴 쓰고, 상시 규칙은 메모리 파일에 둡니다.

돌아보면 이 네 가지는 시리즈 내내 배운 것들의 팀 버전입니다. 계획 먼저 세우기, 작업에 맞는 모델 고르기, 검증 자동화하기, 컨텍스트 다이어트하기 — 혼자 쓸 때 유용했던 원칙들이 팀에서는 팀원 수만큼 증폭됩니다. 좋은 습관도, 나쁜 습관도 함께 곱해진다는 것 — 그것이 Agent Teams를 다룰 때 가장 먼저 기억할 점입니다.
